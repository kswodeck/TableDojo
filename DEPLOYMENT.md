# Deploying Table Dojo

Target: **$0/month.** Vercel Hobby for the web app, Render's free instance for the API, MongoDB Atlas's
free cluster for data. The only recurring cost is the domain (~$12/year).

| Piece | Where | Cost |
| --- | --- | --- |
| Web (Next.js) | Vercel Hobby | Free |
| API (Express) | Render free instance | Free |
| Database | MongoDB Atlas free cluster | Free |
| Email (optional) | Resend free tier | Free |

**Know this going in:** the free Render instance suspends after 15 minutes of inactivity and takes up
to a minute to wake. The app is built to absorb that — the home page, all three `/learn` guides and
all three `/practice` tables run entirely in the browser and work while the API is asleep. Only
sign-in, ranked play, the leaderboard and the blog wait on it, and the UI says so while it boots.

---

## 1. Database — MongoDB Atlas

1. Create an account, then a **free cluster** (M0, 512 MB — free forever, no card).
2. **Database Access** → add a user with a generated password. Save it.
3. **Network Access** → allow `0.0.0.0/0`.
   Render's free instances have no static outbound IP, so there is nothing narrower to allow-list.
   The database is still protected by credentials and TLS.
4. Copy the connection string and append the database name:
   ```
   mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/tabledojo?retryWrites=true&w=majority
   ```

Indexes are declared in the Mongoose schemas and are created on first connect. Nothing to run by hand.

## 2. API — Render

The repo has a [`render.yaml`](render.yaml) blueprint.

1. Render dashboard → **New → Blueprint** → select this repo. It reads `render.yaml` and creates the
   `tabledojo-api` service on the free plan.
2. Fill in the variables marked `sync: false`:

   | Variable | Value |
   | --- | --- |
   | `MONGODB_URI` | the Atlas string from step 1 |
   | `CORS_ORIGINS` | your Vercel URL for now, e.g. `https://tabledojo.vercel.app` |
   | `WEB_ORIGIN` | same |
   | `COOKIE_SAMESITE` | `none` for now — see step 4 |

   `SESSION_SECRET` is generated by Render. `TRUST_PROXY=1` and `NODE_ENV=production` are already set
   in the blueprint; both matter, see [Gotchas](#gotchas).
3. Deploy, then confirm `https://<your-service>.onrender.com/health` returns `{"status":"ok",...}`.

## 3. Web — Vercel

1. Vercel → **Add New → Project** → import this repo.
2. **Root Directory: `apps/web`.** This is the one setting that matters. Vercel detects the npm
   workspace and installs from the repo root; the `prebuild` script compiles
   `@tabledojo/game-logic` before `next build`.
3. Environment variables:

   | Variable | Value |
   | --- | --- |
   | `NEXT_PUBLIC_API_URL` | `https://<your-service>.onrender.com` |
   | `API_INTERNAL_URL` | same |

4. Deploy.

> **`NEXT_PUBLIC_*` variables are inlined at build time.** Changing one in the dashboard does nothing
> until you redeploy. If the browser is calling `localhost:5000` in production, this is why.

## 4. Domain, and the cookie problem

Auth uses `httpOnly` session cookies sent with `credentials: 'include'`. **Where the two services live
decides whether login works.**

- `tabledojo.vercel.app` + `tabledojo-api.onrender.com` are **different sites**. The cookie is
  third-party, so it needs `SameSite=None; Secure` — which Safari blocks by default and Chrome
  restricts. Logins will work unreliably, and worst of all, inconsistently.
- `tabledojo.com` + `api.tabledojo.com` are the **same site**. `SameSite=Lax` works everywhere.

So the platform hostnames are fine for a smoke test with `COOKIE_SAMESITE=none`, but **attach the
domain before you show anyone.**

Once you own the domain:

1. **Vercel** → project → Domains → add `tabledojo.com` and `www.tabledojo.com`. Follow its DNS
   instructions.
2. **Render** → service → Settings → Custom Domain → add `api.tabledojo.com`. Add the `CNAME` it gives
   you. Free instances support custom domains and TLS.
3. Update Render's env vars and redeploy:
   ```
   CORS_ORIGINS=https://tabledojo.com,https://www.tabledojo.com
   WEB_ORIGIN=https://tabledojo.com
   COOKIE_SAMESITE=lax
   ```
   Leave `COOKIE_DOMAIN` unset unless you need the cookie shared across subdomains.
4. Update Vercel's `NEXT_PUBLIC_API_URL` and `API_INTERNAL_URL` to `https://api.tabledojo.com`, then
   **redeploy** (see the build-time note above).

## 5. Email — optional

Password reset and the contact form work without this: with `SMTP_URL` unset the API logs the message
instead of sending it, and the UI behaves identically. To send for real, create a
[Resend](https://resend.com) account (3,000 emails/month free), verify your domain, and set on Render:

```
SMTP_URL=smtp://resend:YOUR_API_KEY@smtp.resend.com:587
MAIL_FROM="Table Dojo <no-reply@tabledojo.com>"
CONTACT_TO=you@example.com
```

## Gotchas

**`TRUST_PROXY=1` is not optional.** Render terminates TLS at its edge and forwards over HTTP. Without
it, Express sees an insecure connection and silently refuses to set `Secure` cookies — so nobody can
log in — and `express-rate-limit` counts every visitor under a single proxy IP, so one active user can
lock out everyone else.

**`NODE_ENV=production` is what enables `Secure` cookies.** It is set in the blueprint; don't remove it.

**Free-tier hours.** Render gives 750 instance-hours per month per workspace. One always-on service
would use ~730, so a single API fits — but a second free service will not.

**Don't add an uptime pinger to defeat the spin-down.** It burns the hour budget, and Render's terms
discourage it. If cold starts start bothering you, the honest fix is the $7/month Starter plan — one
dropdown, no code changes.

**Atlas free-tier storage is 512 MB.** Sessions and expired game sessions clean themselves up via TTL
indexes, so the practical limit is user and post volume. You will not approach it.

## Verifying a deploy

```bash
curl https://api.tabledojo.com/health
# {"status":"ok","uptime":...}

curl -i https://api.tabledojo.com/api/auth/me
# {"user":null} — and a td.sid cookie with Secure; HttpOnly; SameSite=Lax
```

Then in the browser: sign up, play a ranked blackjack hand, and check the leaderboard shows your coins.
That exercises the cookie, the database write and the server-authoritative game path in one pass.

## Rolling back

Both platforms keep previous deploys. Vercel: Deployments → ⋯ → Promote to Production. Render:
Events → Rollback. Neither touches the database, so a rollback is safe unless a schema change shipped
in between.
